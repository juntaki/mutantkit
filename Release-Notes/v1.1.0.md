## Highlights

- SwiftPM projects with local path dependencies: a package that declares
  `.package(path: "../Sibling")` for a directory outside the project root
  now builds and tests inside its sandboxes. Previously the sandbox held
  only the project, so the unmutated build failed and the run ended in a
  baseline mismatch (#77). The project and each local package it reads are
  now laid out in every sandbox at their original relative positions;
  `dry-run` and `run` print a `Local packages:` line naming them.
  `project.path` is now honored by the sandboxed build and test steps, not
  only by plan-time source discovery (#78).
- Per-test coverage no longer all-or-nothing. A test that cannot be proven
  in isolation (order-dependent, crashed, timed out, unreadable coverage)
  is retried once; if it still cannot be proven, the rest of the
  measurement is kept and that test is included in every mutant's test
  selection. No mutant is classified `noCoverage` from such a map. The run
  says so on stderr and in `report.json`'s `operationalIssues`
  (`perTestCoverageIncomplete`) (#63).
- The per-test coverage cache is keyed on what the measurement depends on
  (project, tests, source tree, toolchain) rather than on the whole
  configuration, so changing `strategy`, `budget`, operators, timeouts or
  report formats no longer re-measures it. It also stores each test
  identifier once instead of once per covered line, and the stored file is
  now deterministic (#63, #65, #66).
- `run` says what it is doing during long steps: whether the coverage
  cache hit or missed (and why), labelled progress with an ETA for the
  per-test coverage pass and for schemata chunks, and, when
  `execution.profile` replaces a value written in `mutantkit.yml`, each
  changed setting with both values (`mutantkit execution-profile` shows
  the same preview). `doctor` now notes that the first coverage
  measurement runs every test in isolation and can exceed the mutant run.
  stdout is line-buffered when piped, so CI logs and `tee` no longer sit
  silent until a 4 KB buffer fills (#64).
- `plan`/`run` no longer warn that "the plan no longer matches the
  configuration" after execution-only edits made between `plan` and `run`
  (`workers`, `selectCoveringTests`, report formats). The warning now
  compares only what decides what gets planned: source scope, operators,
  budget and diff base (#65).
- Xcode: when no scheme can be resolved, the message now says what
  happened (killed at the time budget, killed by a signal, non-zero exit,
  incomplete output, or genuinely no schemes) instead of always telling
  you to mark a scheme shared (#67). A schemata chunk's build receipt no
  longer fails because the run's simulator device was deleted mid-run
  (#74). A failed schemata baseline now keeps the real baseline record,
  commands and test summary in the report instead of an empty one (#72).
- Dependencies: swift-syntax 603 -> 604.0.0 (#73); `ToolVersion` and
  `mutantkit --version` now derive their plan/report schema versions from
  the schema constants rather than a second copy.
- Internal restructuring of the run engine and Xcode adapter, a bilingual
  README, and CI/workflow maintenance (#70, #75, #76, #79).

## Upgrade impact

Apart from the absolute-path case under "Compatibility changes", nothing
needs to be edited: `mutantkit.yml`, CLI flags, exit-code meanings,
plan/report schema versions (still 1) and the mutation ID derivation are
unchanged for the same source.

- Caches and checkpoints from v1.0.3 are not reused. Every run identity
  (checkpoint, result cache, coverage cache) now also covers the project's
  sandbox position and the content of any local packages outside the
  project, so the identity differs from v1.0.3's for every project, with or
  without local packages. A stale entry is simply not found (the identity
  is part of the file name, and an unreadable or mismatched cache entry is
  treated as a miss); it is never an error. Consequences: the first run
  re-measures per-test coverage and re-evaluates mutants, and an
  interrupted v1.0.3 run does not resume. Old files under `.mutantkit/` are
  left in place and can be deleted. Editing a local package outside the
  project now invalidates the cache and checkpoint, as editing the project
  does.
- Plans generated by v1.0.3 still load and run. `run` and `verify` print
  compatibility warnings (different tool version, swift-syntax 603.0.0 vs
  604.0.0, and, because the plan records no planning-settings hash, usually
  a planning-settings notice); they do not change the exit code. Re-plan to
  clear them. Plan IDs are computed differently (`v2`, from planning
  settings only), so re-planning an unchanged tree yields a different
  `planID` than v1.0.3 did. Source-location changes caused by parser or
  toolchain differences can make an individual planned mutation
  inapplicable; it is then reported as not applied (with a diagnosis) and is
  not scored.
- `report.json` `operationalIssues` can contain a new `kind`,
  `perTestCoverageIncomplete`. A consumer that rejects unknown kinds should
  accept it. `plan.json` may gain an optional `planningHash` field, written
  only when it differs from `configurationHash`.
- Minimum requirements are unchanged: macOS 14+, Apple Silicon, Swift 6.0+
  (`swift-tools-version:6.0`).

## Compatibility changes

SwiftPM local path dependencies are now checked before a run, and a
dependency that MutantKit cannot reproduce inside the mutation sandbox is
refused with the reason (exit 1) instead of proceeding. `run`, `dry-run`,
`reproduce` and `doctor` evaluate the package manifests to do this.

- **Absolute local-package paths** (`.package(path: "/abs/path/Dep")`) are
  refused. A v1.0.3 run with such a dependency completed, but the absolute
  path points outside the sandbox, so the dependency was not a copy carried
  with the sandbox and was not part of the run's verified input. This is the one case in which a configuration that
  worked on v1.0.3 now fails early. Declare the package by a relative path
  instead, for example `.package(path: "../Dep")`.
- Relative local packages such as `.package(path: "../Sibling")`, beside or
  inside the project, are supported: they are laid out in every sandbox at
  their original relative positions and are part of the run identity.
  On v1.0.3 this layout failed with a baseline build error.
- A dependency reached through a symbolic link, a dependency directory with no
  `Package.swift`, a dependency that contains or points back at the project, a
  symbolic link inside an external package that points outside it, and
  manifests whose dependency list cannot be read are refused with the reason.
  For the symbolic-link and missing-`Package.swift` layouts, v1.0.3 also
  failed (the unmutated build exited 1 without a compiler diagnostic); they
  now fail up front with an explanation.

## Breaking changes

No documented CLI flag, configuration key, schema version or JSON contract
has been removed or changed incompatibly. See "Compatibility changes" above
for the one run-time behaviour change.
